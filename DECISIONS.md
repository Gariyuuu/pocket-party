### D-001: Every user, guest or not, is a real Supabase Auth user (anonymous auth as the identity substrate)

- **Status:** Adopted (implemented, unlikely to be reconsidered without a major rework).
- **Context:** the app's core promise is "play instantly with no signup." Something still needs to identify a player for RLS, room membership, and stats.
- **Decision:** every visitor is auto-signed-in anonymously (`middleware.ts` → `signInAnonymously()`) on first request, getting a real `auth.users` row and a matching `profiles` row via `handle_new_user()`. Optional account linking later upgrades the *same* user id rather than creating a new one.
- **Reasoning (Inferred, high confidence):** this lets every RLS policy in the entire schema use a single uniform check (`auth.uid() = ...`) regardless of whether the caller is a guest or a "real" account — no separate guest-vs-authenticated code path anywhere in the authorization layer. Confirmed as the load-bearing reason by the account-linking code specifically preserving `auth.uid()` across the upgrade (`updateUser`/`linkIdentity`) rather than creating a new profile and migrating data.
- **Alternatives considered (Inferred, not directly evidenced):** a separate "guest session" mechanism outside Supabase Auth (e.g. a signed cookie with no `auth.users` row) — would have required either duplicating every RLS policy for a guest-specific path or bypassing RLS for guests entirely (a security downgrade). No evidence this was ever tried; inferred as the likely alternative any developer would consider and reject.
- **Consequences:** `profiles` must be fully publicly readable (any authenticated, including anonymous, user can read any profile) since there's no other way to show opponent nicknames/stats without a service-role round-trip for every read. This is a deliberate privacy tradeoff, documented in `SECURITY.md`.
- **Affected files:** `src/middleware.ts`, `supabase/migrations/20260805000002_profiles.sql`, `src/components/profile/account-linking.tsx`.

### D-002: Server-authoritative match state via a single generic `GameEngine` interface

- **Status:** Adopted.
- **Context:** 10 different games need turn/move validation that can't be trusted to the client.
- **Decision:** every game implements one shared interface (`createInitialState`, `applyAction`, `checkOutcome`, optional `getBotAction`), and all state mutation flows through one server function (`match-runtime.ts`'s `submitAction`) rather than each game having its own bespoke API route.
- **Reasoning (Inferred, high confidence, evidenced by the pattern's consistency across all 10 games and the `games/core/` abstraction existing at all):** avoids re-implementing anti-cheat/validation/persistence logic 10 times; makes adding an 11th game a matter of implementing one interface rather than building a new subsystem.
- **Alternatives considered (Inferred):** per-game API routes/tables — would have meant 10x the surface area for the same validation logic, and no shared audit trail.
- **Consequences:** the interface's genericness forces `any`-typed dispatch points (`games/core/engines.ts`, `game-surface.tsx`, `solo-game-shell.tsx`), trading some compile-time type safety at those specific boundaries for a single, consistent server-side security model everywhere else. Documented as an accepted tradeoff via the `eslint-disable` comments at each site, not an oversight.
- **Affected files:** `src/games/core/game-engine.ts`, `src/games/core/engines.ts`, `src/lib/multiplayer/match-runtime.ts`, every `src/games/*/engine.ts`.

### D-003: Two different real-time mechanisms for two different data shapes (Postgres Changes vs. Broadcast)

- **Status:** Adopted.
- **Context:** most games need durable, validated, turn-based sync; two games (Orb Hockey, Quick Draw) need much higher-frequency, low-latency updates (paddle/puck position, pen strokes) where durability doesn't matter and Postgres round-trip latency would hurt gameplay feel.
- **Decision:** discrete/contestable/must-be-fair state (score, turn order, outcomes) goes through Postgres + RLS + server validation, synced to clients via Realtime Postgres Changes. Continuous/uncontestable/cosmetic-if-dropped state (live paddle position, live pen strokes) is sent directly client-to-client via Realtime Broadcast, never touching Postgres.
- **Reasoning (Inferred from the architecture itself plus the explicit comment on Orb Hockey's goal-reporting check, which states the concern directly: a client can't be trusted to self-report a real-time-physics-derived outcome, so the *discrete event* — a goal — is what goes through the authoritative path, while the *continuous simulation* driving toward that event does not need to be).**
- **Alternatives considered (Inferred):** routing paddle/pen-position updates through Postgres too, for architectural uniformity — would very likely have introduced enough latency to hurt these two games' feel, at zero benefit since that data was never meant to be replayed/audited anyway.
- **Consequences:** the codebase has a genuine architectural split that a future maintainer must understand (not a bug, but easy to mistake for one if unaware) — "why does this one game sync differently?" See `ARCHITECTURE.md`.
- **Affected files:** `src/games/orb-hockey/board.tsx`, `src/games/quick-draw/board.tsx` (or wherever Quick Draw's broadcast logic lives — not independently re-confirmed by filename in this pass, **Needs confirmation**), `src/lib/multiplayer/match-runtime.ts` (the Orb Hockey `score-goal` seat-1-only check).

### D-004: Match history keyed off `match_players`, not `room_players` — and `matches.room_id` made nullable (migration 20260805000010)

- **Status:** Adopted, superseding an earlier design.
- **Context:** the original schema (migrations 006-007) made every match/leaderboard/achievement RLS policy check visibility by joining through `room_players` (i.e., "can you see this match's data if you can see the room it was played in"). Rooms are cleaned up by `cleanup_expired_rooms()` after they go idle, and `matches.room_id` originally cascade-deleted.
- **Decision:** `matches.room_id` was changed to nullable with `on delete set null` (instead of `on delete cascade`), and the 4 dependent SELECT policies (`matches`, `match_players`, `game_states`, `match_actions`) were dropped and recreated to check `match_players` (which is never touched by room cleanup) instead of `room_players` (which is).
- **Reasoning (Verified — quoted almost verbatim from the migration's own header comment):** "Room cleanup... deletes old rooms, and matches.room_id originally cascaded from rooms — meaning match history, the leaderboard's source data, and achievements evidence would all vanish the moment a finished room aged out." The fix's own comment further notes: "'which room was this played in' was never load-bearing for anything but the live game, so losing it costs nothing."
- **This was a real, self-discovered bug fix**, not a hypothetical or defensive-only migration — the original design would have actively deleted completed-match data on a normal, expected cleanup cycle.
- **Alternatives considered (Inferred):** excluding `matches`/related rows from `cleanup_expired_rooms()`'s delete criteria instead of changing the FK/RLS — rejected implicitly, likely because the cleanup function targets `rooms` directly and any historical match data needs to survive independently of whether its room specifically was targeted, not by carving out exceptions in the cleanup logic itself.
- **Consequences:** do not revert this migration's changes without preserving its intent — see `CLAUDE.md`'s "DO NOT CHANGE WITHOUT REVIEW."
- **Affected files:** `supabase/migrations/20260805000010_preserve_match_history.sql` (and everything it modifies from migration 006).

### D-005: Determinism via a single seeded PRNG, with `Math.random()` deliberately allowed only for bot "thinking"

- **Status:** Adopted.
- **Context:** server and every client must agree on any randomized game outcome (initial shuffles, tile generation) for fairness and replay consistency; but bot move selection doesn't need to be reproducible.
- **Decision:** all game-affecting randomness derives from `games/core/rng.ts`'s seeded PRNG, keyed off a per-match `seed` stored on the `matches` row and threaded through `createInitialState`. Bot decision-making is the one explicitly carved-out exception, using plain `Math.random()`.
- **Reasoning (Inferred, moderate-to-high confidence — evidenced by the consistency of the pattern across all engines and the clean separation of "engine randomness" from "bot randomness"):** a shared, auditable seed lets the server's authoritative state and every client's rendering derive from the same source of truth without needing to transmit every intermediate random draw; bot moves have no fairness stake since a bot isn't a human player whose outcome needs to be provably fair to anyone.
- **Consequences:** any engine code that introduces `Math.random()` outside of bot logic silently breaks this guarantee without necessarily failing any existing test (a real risk called out explicitly in `ARCHITECTURE.md`'s "Major architectural risks").
- **Affected files:** `src/games/core/rng.ts`, `src/lib/multiplayer/match-runtime.ts` (`randomSeed()` call site), every `engine.ts`'s `createInitialState`.

### D-006: Procedurally-generated assets over shipped binary assets, wherever practical

- **Status:** Adopted, applied twice (audio, theme backgrounds).
- **Context:** the app needs sound effects/music and, later, theme-wheel background images.
- **Decision:** audio is synthesized at runtime as WAV tones (`lib/audio/tone.ts`) rather than shipped as audio files; theme backgrounds are generated by a hand-rolled PNG encoder using only Node's built-in `zlib` (`scripts/generate-theme-backgrounds.js`) rather than fetched or hand-designed and shipped as static images, then committed as pre-generated PNGs in `public/themes/`.
- **Reasoning (Inferred from the pattern's repetition across two unrelated feature areas, treated as a deliberate project-wide preference rather than a coincidence):** avoids external asset licensing/sourcing concerns, avoids a runtime dependency on an image/audio library, keeps the repository's binary footprint minimal and every visual/audio asset fully reproducible from source via a checked-in script (`npm run generate:themes`).
- **Consequences:** anyone changing a theme's colors must remember to re-run `npm run generate:themes` — the PNGs are committed outputs, not derived at build/request time, so they can silently go stale relative to `theme-packs.ts` if someone edits the palette data without regenerating.
- **Affected files:** `src/lib/audio/tone.ts`, `scripts/generate-theme-backgrounds.js`, `public/themes/*.png`.

### D-007: In-memory, per-instance rate limiting rather than a distributed store

- **Status:** Adopted, explicitly flagged as temporary/scale-limited by its own author.
- **Context:** room creation, room joining, and match actions all need abuse throttling.
- **Decision:** a simple in-memory fixed-window counter (`lib/multiplayer/rate-limit.ts`), not backed by Redis/Vercel KV/any shared store.
- **Reasoning (Verified — quoted from the file's own header comment):** "good enough to blunt room-code brute forcing and action spam for Phase 1... Swap for Upstash Redis (or Vercel KV) behind this same signature before scaling past one region/instance."
- **This is a knowingly-temporary decision, not an oversight** — the file documents its own successor plan and the exact conditions under which it should be replaced.
- **Affected files:** `src/lib/multiplayer/rate-limit.ts`.

### D-010: Migrate off Supabase entirely — Clerk (accounts) + Neon/Drizzle (database) + PartyKit/Cloudflare (realtime)

- **Status:** Adopted, in progress. **Verified from conversation — this is the user's own explicit decision, not inferred.**
- **Context:** the account-switch checkpoint (see `SESSION_LOG.md`) surfaced a blocker: a Supabase project existed but was linked from the wrong directory, so the natural next step was "connect a real Supabase project." When asked how to proceed, the user stated directly: **"use clerk and neon i cant use supabase"** — a hard constraint, not a preference (the "i cant" wording — not "i'd rather not" — was taken at face value; no attempt was made to talk them out of it or to ask why). This reopens D-001, D-003, and D-004 above, all of which were written assuming Supabase would remain the backend.
- **Two follow-up decisions the user made explicitly when asked (via `AskUserQuestion`), because the swap has real product/architecture consequences and isn't just a drop-in replacement:**
  1. **Guest play:** "Keep true no-signup guest play" — Clerk has no anonymous-session primitive equivalent to Supabase's `signInAnonymously()`, so guest identity is hand-rolled (a cookie-based id, outside Clerk entirely) and Clerk is used only when a player chooses to create a real, persistent account.
  2. **Realtime transport:** "PartyKit / Cloudflare (Recommended given your other projects)" — chosen explicitly because the user has a working precedent in the sibling project `chamber-seven` (`partyserver` + `wrangler`, deployed as a Cloudflare Worker, `partysocket` on the client). This was offered as the recommended option specifically *because* of that precedent, and the user picked it.
- **Reasoning for the overall architecture (this auditor's design, built on the user's two constraints above, not independently dictated by the user beyond what's quoted):**
  - `profiles.id` is decoupled from any auth provider (a plain generated uuid) with nullable `clerkUserId`/`guestCookieId` columns, so "linking" a guest to a real account is just attaching a `clerkUserId` to the *existing* profile row — preserving the same stats-continuity guarantee D-001 relied on `auth.uid()` for, without Supabase providing it for free anymore.
  - Neon has no RLS-to-JWT wiring, so **every authorization check that used to be an RLS policy becomes explicit application code.** This was confirmed field-by-field by an exploration pass (see `SESSION_LOG.md`) — the exact list of app-code call sites that currently assume RLS is doing the work (`room-actions.ts`'s four client-side mutations, `use-resolve-room-id.ts`, the `leave_room()` function's internal `auth.uid()` dependency) is the migration's real risk surface, not the schema translation itself.
  - PartyKit absorbs both what `match-runtime.ts` did (room/match orchestration) *and* what Supabase Realtime Broadcast did for Orb Hockey/Quick Draw (both become just more message types on the same per-room Durable Object connection) — net simplification from two sync mechanisms to one.
  - Neon's serverless driver (`@neondatabase/serverless`) is HTTP-based, not raw-TCP, so it works unmodified from both Next.js server code and a Cloudflare Worker — this is why the PartyKit Main durable object (Phase 3) can talk to Neon directly for match finalization, mirroring chamber-seven's already-proven "Durable Object → best-effort side-call on match end" pattern (there, into a second Durable Object; here, into Postgres).
- **Alternatives considered and explicitly rejected by the user:** continuing with Supabase in any form (the "i cant" framing forecloses this, reason not stated — do not assume it was cost, ToS, a past incident, or a technical limitation; it is simply unknown and should be asked about only if it becomes newly relevant, not re-litigated).
- **Alternatives considered for realtime, not chosen:** Pusher/Ably (hosted pub-sub, offered as an option) and a plain custom WebSocket server on Vercel/Node (offered as an option, noted as a poor fit for Vercel's serverless model) — both were presented alongside PartyKit in the `AskUserQuestion` call and not picked.
- **Consequences:** this supersedes D-001 (identity substrate), D-003 (Postgres-Changes-vs-Broadcast split — the *reasoning* about discrete-vs-continuous state still holds, just implemented differently), and D-004 (the `match_players`-vs-`room_players` RLS visibility fix — the *lesson* "don't key match-history visibility off something that cascade-deletes" still applies and must be re-derived correctly in the new schema; the specific RLS-policy mechanism it fixed no longer exists). D-001/D-003/D-004 are left in this log unedited, as a record of what was true before this decision — do not delete them.
- **Affected files:** effectively the entire backend layer. See `PROJECT_STATE.md` for the phased execution plan and exactly which phase is complete as of the last update to that file.

#### Phase 1 schema-translation decisions (implementation detail, this session)

- **`leaderboard_entries.winRate`** kept as a Postgres generated column (portable as-is — Neon is plain Postgres, this required no change).
- **3 Supabase `security definer` functions dropped from the schema, not ported 1:1:** `handle_new_user()` (trigger on `auth.users` insert — no `auth.users` table exists under Neon; profile provisioning moves to application code in Phase 2), `leave_room()` and `cleanup_expired_rooms()` (both relied on or were adjacent to session-scoped `auth.uid()` availability that Postgres itself no longer has any way to know under Neon; both become plain parameterized TypeScript functions in Phase 3, taking the actor id as an explicit argument instead of reading it from a session).

### D-011: Phase 2 identity-layer design (this session's implementation choices, not separately confirmed with the user beyond the two constraints already recorded in D-010)

- **Status:** Adopted, implemented (Phase 2 of T-003 done).
- **Context:** D-010 fixed two things by direct user instruction — guest play must stay no-signup, and it must not go through Clerk. Everything else about *how* a guest's identity coexists with Clerk, and *how* linking preserves stats, was left to be designed, since Clerk has no primitive equivalent to Supabase's "same `auth.uid()`, just flip `is_anonymous`" trick.
- **Decision — three identity mechanisms run side by side during the migration, in `src/middleware.ts`:** Clerk's own middleware (session detection for real accounts), a hand-rolled `guest_id` cookie (`src/lib/identity/guest-cookie.ts` — a plain `crypto.randomUUID()`, httpOnly, 1-year expiry, not a secret since it grants no permission by itself), and the **original Supabase anonymous-session bootstrap, left completely untouched**. The third one exists only because the room/match code paths are still 100% Supabase-backed (Phase 3/4 not done yet) and removing it now would break the one part of the app that still functionally works end-to-end at the code level. This mirrors Phase 1's "purely additive, don't break what's running" approach.
- **Decision — `profiles.id` is the unification point, resolved by `src/lib/identity/get-current-actor.ts`:** on every call, resolve Clerk session first (if any), else the guest cookie. The one genuinely tricky piece: **the first time a guest signs up with Clerk, there is a race between "find my existing Clerk-linked profile" (none yet) and "find my existing guest profile" (exists, has stats)** — resolved by looking up the guest's profile via the `guest_id` cookie and checking it's still unclaimed (`clerkUserId is null`) before attaching the new `clerkUserId` to that *same row*, preserving `id` and every stat tied to it. A guest profile already claimed by a *different* Clerk user is deliberately never re-claimed (checked explicitly, not just assumed) — this prevents one browser's guest history from ever being silently reassigned across two different real accounts.
- **Decision — no Clerk webhook for profile provisioning.** Considered and rejected in favor of resolving/claiming lazily, synchronously, inside `get-current-actor.ts` itself, the next time any code path needs to know who the current actor is. Reasoning: a webhook needs a public URL to receive `user.created` events, which doesn't exist yet (no deployment), and the lazy approach is a closer match to how the Supabase-era middleware already worked (ensure identity synchronously, on request, not via an async side channel).
- **Decision — `account-linking.tsx` was rebuilt around Clerk's own prebuilt modal UI** (`useClerk().openSignUp()` / `openSignIn()`), not a hand-rolled email/Google form the way the Supabase version was. Reasoning: Clerk's SDK provides this UI out of the box (whatever providers are configured in the Clerk dashboard show up automatically), so hand-rolling the old email-input-plus-Google-button UI would just be re-implementing something Clerk already gives for free, with no benefit. The component no longer takes an `isGuest` prop from its parent (`profile-header.tsx`, still Supabase-driven) — it reads `useUser().isSignedIn` from Clerk directly, decoupling it entirely from the Supabase-sourced data around it on that page. **This is a deliberately accepted, temporary inconsistency:** `/profile` now has a Clerk-driven identity widget sitting next to Supabase-driven stats/match-history, until Phase 4 moves the rest of that page onto the new stack. Verified this doesn't break anything today: `typecheck`/`lint`/`test`/`build` all pass, and the dev server still fails at exactly the same point it did before (the Supabase env-var check) when run with no `.env.local`, confirming the new Clerk/guest-cookie code doesn't interfere with what already worked.
- **Not yet verified against a real Clerk application** — no Clerk keys exist yet. The exact behavior of `openSignUp`/`openSignIn`'s modal, and the claim logic's correctness under a real sign-up, are unverified beyond typechecking and passing the existing automated suite.
- **Affected files:** `src/lib/identity/guest-cookie.ts` (new), `src/lib/identity/get-current-actor.ts` (new), `src/middleware.ts` (rewritten), `src/app/layout.tsx` (wrapped in `ClerkProvider`), `src/components/profile/account-linking.tsx` (rewritten), `src/components/profile/profile-header.tsx` (one-line fix — stopped passing the now-removed `isGuest` prop).

### D-012: Simplify the Neon schema — drop `rooms`, `room_players`, `game_states`, `match_actions` (Phase 3)

- **Status:** Adopted, implemented. Revises Phase 1's schema (never applied anywhere, so revising in place was safe — see D-010's Phase 1 notes on that same rule).
- **Context:** Phase 1 translated all 11 Supabase tables into Drizzle 1:1, including 4 tables (`rooms`, `room_players`, `game_states`, `match_actions`) that existed only to give Postgres+RLS something to hold the *live* state of an in-progress room/match. Once Phase 3 designed PartyKit's `Main` durable object as that live state's owner (one JSON blob per room, in Durable Object storage — see D-013), those 4 tables had no remaining reader or writer anywhere in the new architecture.
- **Decision:** delete all 4 tables from the schema. Neon's role narrows to exactly what's true forever, not true right now: `profiles`, `matches` + `match_players` (a summary row per finished match, written once by `finalizeMatch()` — not a live/updated-during-play row anymore), `achievements` + `profile_achievements`, `recent_players`, `leaderboard_entries`. `matches.roomId` (a FK to the deleted `rooms` table) became `matches.roomCode` (plain text, no FK, informational only) — the original Supabase-era migration's own reasoning for a similar change ("which room this was played in was never load-bearing for anything but the live game") still applies and was the deciding factor here too.
- **Also renamed `match_players.playerId` → `profileId`** for consistency with every other table's foreign-key naming (a leftover from Phase 1's literal 1:1 translation of the old `player_id` column name, caught while wiring Phase 3's Drizzle queries against it).
- **Consequences:** a completed match's full action-by-action replay log no longer exists anywhere once its room's Durable Object goes idle and clears its storage (see D-013's `onAlarm`) — this app never had a "watch the replay" feature, so nothing user-facing is lost, but this is a real reduction in retained data compared to the Supabase-era design, worth knowing if a future feature ever wants replay data.
- **Affected files:** `src/lib/db/schema.ts`, `drizzle/0000_hot_proudstar.sql` (regenerated, still never applied anywhere).

### D-013: Phase 3 — PartyKit `Main` durable object design

- **Status:** Adopted, implemented (Phase 3 of T-003 done, with two explicitly-scoped-out follow-ups — see below).
- **Context:** T-003's plan called for porting `match-runtime.ts`'s orchestration into a PartyKit durable object modeled on the sibling project `chamber-seven`'s working `partyserver`+`wrangler` setup, and moving the client off Supabase Realtime entirely.
- **Decision — one `Main` durable object per room, addressed by room code as the party "name."** This collapses `roomId` (a separate UUID) and `code` into one concept — a room's *address* is its code, there's no separate id to resolve. `src/lib/party/room-state.ts` holds the pure decision logic (join/ready/select-game/start/action/rematch/return-to-lobby/leave — literally the same operations `match-runtime.ts` + `create-room.ts` + `join-room.ts` + `room-actions.ts` + the `leave_room()`/`cleanup_expired_rooms()` Postgres functions used to split across 6+ files) as plain, I/O-free functions; `party/game.ts`'s `Main` class is a thin shell (storage get/put, broadcast, rate limiting, the Neon writes on match end). This is a real improvement over the original, not just a port: the orchestration logic is now directly unit-testable (`tests/unit/party-room-state.test.ts`, 16 tests) — `match-runtime.ts` never had that.
- **Decision — a signed, short-lived HMAC token bridges identity into the Worker** (`src/lib/party/room-token.ts`, Web Crypto only — isomorphic between Next.js and the Worker, same reasoning as `src/lib/db/client.ts`'s choice of Neon's HTTP driver). Necessary because the Durable Object can't call Clerk's Next.js-oriented SDK, and needs to trust guests too, which Clerk doesn't cover. `GET /api/identity` mints one (1-hour expiry) from whatever `get-current-actor.ts` resolves; `usePartyRoom` fetches a fresh one on every (re)connection attempt via `usePartySocket`'s `query` callback.
- **Decision — match participants are snapshotted at match start, independent of the live roster** (`StoredMatch.participants`). Caught and fixed *during* this session, before it shipped: an earlier draft derived "who's in this match" from `state.players` at finalization time, which is wrong — `leaveRoom()` removes a player from the roster entirely, so anyone who left mid-match would have silently vanished from their own match's finalization (no score/result/achievement update) by the time it ended. The snapshot fixes this; `applyGameAction`'s participant check was also switched to read the snapshot, not the live roster, so a departed player can no longer submit actions but their match record stays intact.
- **Decision — one broadcast-full-state-on-every-change protocol** (`src/lib/party/protocol.ts`'s `"state"` message), not a diffing protocol — directly mirrors `chamber-seven`'s `Main.broadcastState()` pattern. Simplest correct option at this app's state sizes (one room + roster + one game's state, well under any practical message-size concern).
- **Decision — request/response correlation for `start`/`action`/`rematch`/`return-to-lobby` uses first-message-wins, not a request id.** There's no id in the wire protocol; `usePartyRoom` stores a single pending resolver and settles it with whichever `"state"` or `"error"` message arrives next. Documented as a deliberate simplification, safe *because* this app's UI only ever has one such call in flight per client (awaits one before allowing another) — would need a real correlation id if that assumption ever stops holding.
- **Decision — idle-room cleanup via a Durable Object alarm** (`onAlarm`, 4-hour idle threshold, matching the old `cleanup_expired_rooms()`'s absolute-expiry number) rather than porting all three of that function's nuanced thresholds (2-hour idle lobby, 30-minute idle finished-room) exactly. A deliberate simplification for time, not a claim that the thresholds don't matter — revisit if idle Durable Object storage cost/lifetime ever becomes a real concern.
- **Explicitly scoped OUT of this session** (both since resolved — see D-014 and D-015):
  1. Orb Hockey's/Quick Draw's board-level Broadcast sync — **done, see D-014.**
  2. The public rooms list's backing mechanism — **done, see D-015.**
- **Not yet verified against a real deployment** — no Neon `DATABASE_URL`, Clerk keys, or Cloudflare account/deployment exist yet. Verified only via `typecheck`/`typecheck:party`/`lint`/`test` (169 passing, 16 new)/`build`/`wrangler deploy --dry-run` (confirms the Worker bundles correctly and the `Main` binding resolves — a real, meaningful check, just not a live one).
- **Affected files:** `party/game.ts`, `party/tsconfig.json`, `wrangler.jsonc`, `src/lib/party/*` (all new), `src/components/landing/create-room-button.tsx`, `join-room-form.tsx`, `src/components/room/room-page-client.tsx`, `lobby.tsx`, `src/components/game-shell/online-game-shell.tsx` (all rewired), `src/lib/multiplayer/match-runtime.ts` + the 5 old room/match API routes + the 4 old Supabase Realtime hooks (all now dead code, not yet removed — Phase 5).

### D-014: Phase 3 Follow-up A — generic broadcast passthrough for Orb Hockey/Quick Draw

- **Status:** Adopted, implemented.
- **Context:** D-013 deferred porting Orb Hockey's and Quick Draw's high-frequency, never-persisted sync (paddle/puck position, pen strokes) onto the PartyKit connection.
- **Decision:** rather than adding game-specific message types to the protocol, `src/lib/party/protocol.ts` gained one generic `{ type: "broadcast"; channel: string; payload: unknown }` message (both directions). `party/game.ts` relays it to every *other* connection unvalidated and unpersisted — no storage read/write, no rate limit — deliberately matching Supabase Broadcast's original `{ self: false }`, trust-the-sender semantics exactly, not tightening or loosening them. `channel` is just whatever string a game picks (`"paddle"`, `"puck-sync"`, `"serve"`, `"stroke"`, `"clear"` today); the server never interprets it, so a future game with similar needs adds zero protocol/server changes, only client-side board code.
- **Reasoning:** a generic passthrough is strictly less code than one message type per event, and matches how Supabase Broadcast itself worked (an arbitrary named-event pub/sub channel, not a fixed schema) — this is a faithful architectural port, not a redesign.
- **Consequences:** `src/components/game-shell/game-surface.tsx` gained an optional `party?: PartyBroadcast` prop (a `Pick` of just `sendBroadcast`/`onBroadcast` from the full `usePartyRoom` hook) threaded to the two boards that need it; both boards had every `getSupabaseBrowserClient()` reference removed. `matchId` remains a prop on both boards (used elsewhere to distinguish solo-vs-online) but no longer drives channel addressing — addressing is now implicit in the single per-room PartySocket connection, which is simpler than the old per-match-id-scoped-channel model.
- **Affected files:** `src/lib/party/protocol.ts`, `party/game.ts`, `src/lib/party/use-party-room.ts`, `src/components/game-shell/game-surface.tsx`, `online-game-shell.tsx`, `src/games/orb-hockey/board.tsx`, `src/games/quick-draw/board.tsx`.

### D-015: Phase 3 Follow-up B — Neon-backed public-rooms directory, not a second Durable Object

- **Status:** Adopted, implemented.
- **Context:** D-012 removed the `rooms` table `/lobby`'s public-rooms browser used to query, with no replacement designed at the time.
- **Decision:** a small `public_room_listings` Neon table — a *discovery index*, not a source of truth (`party/game.ts`'s `Main` durable object remains the only authoritative owner of real room state). A row exists if and only if a room is currently public **and** still in its lobby (not yet started); `saveState()` in `party/game.ts` calls `syncPublicListing()` (`src/lib/party/public-rooms.ts`) after *every* state-changing message, upserting or deleting the row based on current `isPublic`/`status`, so there's exactly one place responsible for keeping the listing in sync rather than one call site per message type to remember. `onAlarm`'s idle-room cleanup also removes the listing.
- **Alternative considered and rejected: a second, chamber-seven-`Leaderboard`-style single-instance Durable Object as the registry.** Would have kept everything inside the Cloudflare/PartyKit world and avoided Neon entirely for this feature, but requires a new DO class, a new `wrangler.jsonc` binding, and inter-DO communication (Worker-to-DO or DO-to-DO fetch) that this codebase hadn't needed before. Rejected in favor of reusing the Neon/Drizzle path `finalize-match.ts` already proved works from inside the Worker — fewer new moving parts, same reliability characteristics, and Neon's HTTP driver already confirmed to work from a Cloudflare Worker.
- **Consequences:** the public-rooms list can lag or briefly show a stale entry if a Neon write fails (wrapped in try/catch in `saveState`, logged, never blocks the room/match itself) — an accepted, documented tradeoff since nothing authorization-sensitive depends on this table. `GET /api/public-rooms` is a plain, unauthenticated read (matching the old Supabase policy's public-read behavior for public rooms) — no participant check needed since only already-public rooms ever have a row.
- **Not yet verified against a real deployment** — no Neon `DATABASE_URL` exists yet; verified only via `typecheck`/`typecheck:party`/`lint`/`test`/`build`/`wrangler deploy --dry-run`.
- **Affected files:** `src/lib/db/schema.ts` (new `publicRoomListings` table), `drizzle/0000_wet_golden_guardian.sql` (regenerated), `src/lib/party/public-rooms.ts` (new), `party/game.ts` (`saveState`/`onAlarm` call sites), `src/app/api/public-rooms/route.ts` (new), `src/components/lobby/public-rooms-list.tsx` (rewritten — joining now navigates with `?autojoin=1` instead of a REST call, matching `create-room-button.tsx`/`join-room-form.tsx`'s pattern).

### D-016: Phase 4 — `/profile`/`/leaderboard` ported to Drizzle reads; `force-dynamic` needed on `/leaderboard`

- **Status:** Adopted, implemented.
- **Context:** D-012/D-013 already moved every *write* path (match finalization, achievements, recent opponents, public-rooms sync) onto Neon/Drizzle. `/profile` and `/leaderboard` were the last two Supabase *reads* left in the live code path.
- **Decision:** `src/app/profile/page.tsx` and `src/app/leaderboard/page.tsx` were rewritten as Server Components querying `getDb()` directly, resolving identity via `getCurrentActor()` instead of `supabase.auth.getUser()`. A new `PATCH /api/profile` route (`src/app/api/profile/route.ts`) replaces `profile-header.tsx`'s old direct Supabase `.update()` calls, since there is no client-side Neon access at all under the new stack (no anon-key/RLS model makes that safe the way it was under Supabase) — every profile edit now round-trips through this route, with identity resolved server-side from `getCurrentActor()`, never trusted from the request body.
- **`profile-header.tsx` redesigned around a server-fed prop instead of self-fetching.** The old version called `useCurrentUserId()` + `getSupabaseBrowserClient()` on mount and did its own `is_guest` reconciliation against `supabase.auth.getUser()` (because Supabase's anonymous-to-real-account flip could lag). Neither problem exists under Clerk/Neon: `profile/page.tsx` (the Server Component) already resolved identity and fetched the profile row before rendering, so it now passes that down as `initialProfile: ProfileData | null`; `getCurrentActor()` resolves `isGuest` correctly and synchronously on every server render, so the old "reload to see it flip" reconciliation logic was deleted outright rather than ported.
- **`leaderboard/page.tsx` needed an explicit `export const dynamic = "force-dynamic"` it never needed before.** The Supabase-era version got dynamic rendering for free from `getSupabaseServerClient()`'s `cookies()` call (any use of `cookies()`/`headers()` opts a Next.js route out of static generation automatically). The Drizzle version has no such call — it's a pure DB read with no request-scoped API — so `next build` tried to statically prerender it at build time and failed on a missing `DATABASE_URL`. Fixed by forcing dynamic rendering explicitly, which also happens to be the semantically correct behavior (leaderboard standings should never be served from a stale static cache). `/profile` did not need the same fix — Clerk's `auth()` (used inside `getCurrentActor()`) reads request headers internally and already forces dynamic rendering, same mechanism, different library.
- **`leaderboardEntries.winRate` (a generated `numeric` column) needed an explicit `Number()` conversion** before reuse of the old `Math.round(winRate * 100)` display math — Neon's HTTP driver (`@neondatabase/serverless` via `drizzle-orm/neon-http`) deserializes Postgres `numeric` as a string, not a JS number, unlike `postgrest`'s JSON encoding on the Supabase side which returned it as a number already.
- **Consequences:** zero Supabase reads remain anywhere in the live code path (rooms/matches, achievements, public-rooms, and now profile/leaderboard are all Neon-backed). The only Supabase code left in the repo is genuinely dead: `src/lib/supabase/*`, `src/lib/multiplayer/*`, the 5 old room/match API routes, `supabase/migrations/*`, and the vestigial anonymous-session block in `middleware.ts` — all scoped for removal in Phase 5.
- **Affected files:** `src/app/profile/page.tsx` (rewritten), `src/app/leaderboard/page.tsx` (rewritten), `src/components/profile/profile-header.tsx` (rewritten), `src/app/api/profile/route.ts` (new). `match-history-list.tsx`, `achievements-grid.tsx`, `recent-opponents-list.tsx` needed no changes — confirmed pure presentational components taking already-shaped props, no Supabase dependency at all.

### D-018: Replace PartyKit/Cloudflare Durable Objects with Ably — cost, not architecture, was the trigger

- **Status:** Adopted, implemented. **Verified from conversation — this is the user's own explicit decision, not inferred.**
- **Context:** the migration described in D-010 through D-017 landed on PartyKit (`partyserver`/`wrangler`, one Durable Object per room) as the realtime transport, explicitly because of working precedent in the sibling project `chamber-seven`. Once the user was walked through what running it live actually required — a Cloudflare account with the **Workers Paid plan, a real $5/month minimum**, since Durable Objects aren't available on Cloudflare's free tier — they pushed back directly: **"do i need cloudflare... why don't I just use like a party code so we don't need all this stuff, is this all really needed."** This is a casual GamePigeon-style friends game, not an app where a mandatory recurring cost for the realtime layer was ever a deliberate tradeoff — it was a byproduct of copying a precedent from a different project, not a requirement unique to this one.
- **Decision, offered and picked directly by the user:** swap to **Ably** (a hosted pub/sub service with a real free tier — no Durable-Object-equivalent cost floor), matching a swap the user had already made once before in a different project (Sound Clash: Supabase → Neon + Drizzle + Clerk + Ably, after hitting Supabase account limits) — same playbook, applied here for a different reason (cost avoidance rather than a platform limit).
- **Alternatives considered and explicitly not chosen:** plain HTTP polling (zero extra services, but a materially worse fit for Orb Hockey's real-time paddle physics, which needs much tighter update latency than a poll interval reasonably provides) and Pusher (a comparable hosted pub/sub competitor to Ably, not chosen simply because Ably had direct precedent in the user's own history and the user picked it by name).
- **The load-bearing architectural consequence, not just a transport swap:** Ably is pure pub/sub with **no compute or storage of its own** — unlike a Durable Object, it cannot run `room-state.ts`'s validation logic or hold a room's live state in memory between messages. This meant Phase 3's design (one stateful Durable Object per room, holding everything) could not be ported as-is; it had to be re-split across a stateless Next.js API route (compute) and a small Neon table (storage), with Ably left to do only what it's actually for: fanning a state update out to every other connected client.
  - **`live_rooms` (new Neon table, `src/lib/db/schema.ts`)** — one JSONB row per active room, holding exactly the same `StoredRoomState` shape a Durable Object used to hold in memory. This is *not* a return to the original Supabase-era `rooms`/`room_players` normalization (D-012's reasoning for collapsing those still holds) — it's a single blob, chosen specifically because `room-state.ts`'s reducer already operated on one JS object, and splitting it back into columns would have been pure churn with no benefit.
  - **`src/app/api/rooms/[code]/action/route.ts`** — replaces `party/game.ts`'s `onMessage` switch almost line-for-line: load state from Neon, delegate to the exact same `room-state.ts` functions (unit tests unchanged, just relocated to `src/lib/realtime/`), save the result, publish it to Ably, return it directly to the caller. **A real simplification surfaced by this rework, not just a port:** because every action is now a plain HTTP request/response, the caller's own action result comes back in the HTTP response itself — there's no more need for `usePartyRoom`'s old first-message-wins WebSocket correlation hack (D-013's documented simplification-with-a-caveat). Only *other* clients need the Ably-published copy.
  - **`GET /api/rooms/[code]`** (new) — a real gap found and fixed *during* this rework, before it shipped: a Durable Object's `onConnect` used to push the current room state automatically the instant a WebSocket connected, which is what let a freshly-loading client (with nothing joined yet) discover the room existed at all. Ably has no equivalent "send me the current state on subscribe" primitive, and without this route the autojoin flow on a brand-new room would deadlock (nothing to trigger a state event without an action, no action without knowing you can act). This route is the direct replacement — a plain, read-only fetch on mount, before the Ably subscription is even established.
  - **`RoomStateEvent.updatedAt`** (new field) — added once the above created a second, independent source of state (the initial GET, plus Ably's ongoing publishes) with no ordering guarantee between them, unlike a single WebSocket connection's inherently ordered message stream. The client (`use-realtime-room.ts`) drops any incoming event older than the last one it applied, rather than risk the UI regressing backward from a late arrival.
- **Identity/auth got simpler, not just different.** The PartyKit design needed a custom-signed HMAC room token (`room-token.ts`, since a Cloudflare Worker can't call Clerk's Next.js-oriented SDK) purely to let the Durable Object learn who was connecting. That constraint is gone: `POST /api/rooms/[code]/action` runs in the same Next.js runtime as `getCurrentActor()` and can just call it directly, the same way `PATCH /api/profile` already did. The only auth token still being minted (`GET /api/ably-token`) is for a genuinely different purpose — authenticating the *browser's connection to Ably itself* — and uses Ably's own token-request mechanism rather than a hand-rolled one.
- **A real, acknowledged regression, not swept under the rug:** presence/disconnect tracking. A Durable Object's `onClose` fired automatically and reliably the moment a WebSocket closed. Ably has a Presence feature, but wiring it in would have meant reconciling a second, independent membership source against the Neon-stored roster — reintroducing complexity to solve a problem this app already has a working precedent for solving more simply: the **pre-PartyKit, Supabase-era design's own `visibilitychange`/`beforeunload` heuristic**. This session ported that same idea forward almost exactly — a `pagehide`-triggered `navigator.sendBeacon` call to a new `"disconnect"` action (`markDisconnected`) — explicitly choosing "bring back a heuristic this app already had success with" over "build new infrastructure to fully replace a capability that cost $5/month to keep." Documented plainly as best-effort, not silently regressed.
- **Idle-room cleanup also reverted to its pre-PartyKit shape.** A Durable Object's `onAlarm` (a per-room, self-scheduling timer) doesn't exist without Durable Objects. `src/app/api/cron/cleanup/route.ts` and `vercel.json`'s hourly cron entry — both deleted in Phase 5 as dead weight once `onAlarm` made them redundant — are back, sweeping `live_rooms` for rows idle past the same 4-hour threshold `onAlarm` used to enforce.
- **A real, non-obvious bundler incompatibility, found and fixed during this rework:** Ably's own bundled output (both its default browser build and its tree-shakeable `ably/modular` build) contains a `super(...args)` call inside an arrow function nested in a constructor — valid, standard JavaScript — that Next.js's React Server Components client-boundary analyzer (`next-flight-client-module-loader`) cannot parse, for *any* client-side npm import of it, static or dynamic. The fix that actually worked: load Ably from Ably's own CDN via a `<script>` tag (`next/script`, rendered by `RoomPageClient`) instead of importing the npm package into the client bundle at all — this keeps webpack/RSC from ever seeing Ably's source. `use-realtime-room.ts` polls for the resulting `window.Ably` global (`waitForAblyGlobal`, 50ms interval, 15s timeout) since there's no synchronous "has the script tag loaded yet" signal available to a hook that isn't the one rendering it. The server side (`src/lib/realtime/ably-server.ts`, running in Node, never touching a browser bundle) is unaffected and still uses the plain npm import.
- **Consequences:** no Cloudflare account, no Workers Paid plan, and no `wrangler` deploy step are needed anywhere in this stack anymore — `npm run dev` alone runs the whole app locally (previously `npm run dev:all` ran two servers). `party/`, `wrangler.jsonc`, `party/tsconfig.json`, and the `partyserver`/`partysocket`/`wrangler`/`concurrently` dependencies are gone. `src/lib/party/*` moved to `src/lib/realtime/*` (renamed since "party" specifically meant "PartyKit," which no longer applies) with every type prefixed `Party*` renamed to `Live*`/`Room*` to match. The one recurring cost this stack has now is whatever Ably's own pricing requires past its free tier at real scale — not evaluated here, since the free tier comfortably covers a casual friends-game's traffic.
- **Affected files:** `src/lib/realtime/*` (moved and adapted from `src/lib/party/*`; new: `ably-server.ts`, `room-store.ts`), `src/app/api/rooms/[code]/route.ts` (new), `src/app/api/rooms/[code]/action/route.ts` (new, replaces `party/game.ts`), `src/app/api/ably-token/route.ts` (new, replaces `src/app/api/identity/route.ts`), `src/app/api/cron/cleanup/route.ts` (re-added), `src/lib/db/schema.ts` (`liveRooms` table added), `src/components/room/room-page-client.tsx` (renders the Ably `<Script>` tag), every component that consumed the old `usePartyRoom`/`PartyBroadcast` types (renamed to `useRealtimeRoom`/`RealtimeBroadcast`), `package.json`, `next.config.ts` (briefly touched with a `transpilePackages` attempt that turned out unnecessary once the CDN-script fix landed — removed again), `vercel.json` (re-added), `.env.example`, `playwright.config.ts` (one `webServer` entry instead of two), `tsconfig.json`/`eslint.config.mjs`/`.gitignore` (Cloudflare-specific entries removed).

## ⚠️ This app is now deployed and live — read this before assuming it's still "never verified" or "not deployed"

Every prior version of this file said "never live-tested"/"not deployed" as a blanket statement. **That is no longer true.** In order, across this session and the one immediately before it:

7. Ran `vercel deploy --prod` — **failed on the first attempt**: Vercel's Hobby plan rejected `vercel.json`'s hourly cron schedule outright (a hard deploy failure, not a warning — "Hobby accounts are limited to daily cron jobs"). Loosened the schedule to once daily, redeployed — succeeded.
8. Confirmed the live URL has no deployment-protection/SSO wall blocking it (an unauthenticated `curl` returned the real page), then re-ran the exact same guest-identity/room-join/leave/Ably-token `curl` smoke test from step 5 against **https://pocket-party-eta.vercel.app** instead of localhost — all passed identically.

**A real bug was found and fixed:** `src/lib/db/seed.ts` imported `getDb()` from `./client.ts`, which has `import "server-only"` at its top. That import throws unconditionally unless a bundler (webpack/turbopack, as used by Next.js) aliases it away for server-side code — `tsx` (what `npm run db:seed` actually runs) does no such aliasing, so the script has apparently never been able to run successfully, from the moment `client.ts` gained that import. This had never surfaced before because nobody had a real `DATABASE_URL` to try it against until now. **Fixed** by having `seed.ts` construct its own `drizzle(neon(getDatabaseUrl()))` client directly (reusing `env.ts`'s `getDatabaseUrl()`, which has no `server-only` import) instead of importing `client.ts`. `client.ts` itself is untouched — the `server-only` guard still protects the actual Next.js app code from an accidental client-component import, which is what it was for.

**A real infrastructure constraint was found and worked around:** `vercel.json`'s cron schedule was hourly (`"0 * * * *"`); Vercel's Hobby plan only allows daily cron jobs, and rejects anything more frequent at deploy time rather than silently downgrading it. Now `"0 3 * * *"` (once daily) — see `DEPLOYMENT.md` for the tradeoff this implies (idle rooms linger up to ~28 hours instead of ~5 before cleanup, which is harmless).

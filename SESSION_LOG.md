- **Account/agent:** Claude Code (this session — continuation of the same conversation, triggered by the user pushing back mid-review of the Cloudflare setup step in the account-setup guide from the previous session: "do i need cloud flare, wait this is gmae pidgeon why dont i just use like a party code so we dont need all this stuff, because is this all rreally needed").

- **Why this wasn't a drop-in transport swap:** Ably is pure pub/sub — it has no compute or storage of its own, unlike a Durable Object, which held room/match state in memory *and* ran the validation logic. Every "where does X live now" question had to be re-answered: room state moved to a new Neon table (`live_rooms`, one JSONB row per active room — not a return to a normalized `rooms`/`room_players` split, consistent with D-012's earlier decision to collapse that); the validation logic that used to run inside a Durable Object's `onMessage` became a stateless `POST /api/rooms/[code]/action` Route Handler that loads state from Neon, delegates to the same unchanged pure reducer, saves, and publishes to Ably; the HMAC room-token scheme (`room-token.ts`, existed only because a Cloudflare Worker couldn't call Clerk's SDK directly) was deleted entirely in favor of `GET /api/ably-token` minting a real Ably `TokenRequest`, since the action route now runs in the same Next.js runtime as Clerk and can call `getCurrentActor()` directly.
- **A real design gap found and fixed before it shipped:** Ably has no equivalent of a Durable Object's `onConnect` automatically pushing current state to a newly-connected client. Traced through the autojoin flow (`room-page-client.tsx` waiting on `party.status === "ready"` before attempting to join) and realized that without an initial fetch, a client with no prior state and no Ably event yet would never have anything to act on — a deadlock. Added `GET /api/rooms/[code]` as the initial-state fetch every client makes once on mount, before its Ably subscription is even established. Because this creates two independent, unordered sources of state (the initial fetch and the ongoing subscription), also added an `updatedAt`-ordering guard on the client so a late-arriving stale event can never overwrite newer state.
- **The bundler-incompatibility investigation (the hardest part of this session):** after wiring up a normal `import Ably from "ably"` in the client hook, `npm run build` failed inside `next-flight-client-module-loader.js` with a parse error. Investigated in order, each hypothesis eliminated before moving to the next: (1) added `transpilePackages: ["ably"]` to `next.config.ts` — no effect, ruled out a transpilation-target mismatch; (2) switched to Ably's `ably/modular` API (`BaseRealtime` + explicit `WebSocketTransport`/`FetchRequest` plugins) — same exact failure at a different line, ruling out the UMD-vs-ESM bundle format as the cause; (3) tried a dynamic `import("ably/modular")` inside a `useEffect` instead of a static top-level import, on the theory that this would avoid RSC's static client-reference tracing — still failed, since webpack traces dynamic imports for its chunk graph regardless, and Next.js's flight-client-loader processes any module destined for the client bundle whether the import is static or dynamic; (4) finally read the actual failing line directly in `node_modules/ably/build/modular/index.mjs` and found the root cause: its `ErrorInfo` class's constructor contains `var __super = (...args) => { super(...args); };` — a legal JS pattern (an arrow function capturing the enclosing constructor's `super` binding) that Next.js's RSC client-boundary parser cannot handle, for **any** client-side import of Ably's compiled output, static or dynamic, UMD or modular. **Fix:** abandoned the npm import entirely for the client bundle; load Ably via `<Script src="https://cdn.ably.com/lib/ably.min-2.js" strategy="afterInteractive" />` (rendered once, in `room-page-client.tsx`, so it covers every room/lobby/match view) and reference the resulting `window.Ably` global. Added `waitForAblyGlobal()` — a short polling helper in the hook, since there's no synchronous "script has finished loading" signal otherwise — with a 15-second timeout before surfacing a load-failure error. Removed the now-unnecessary `transpilePackages` config. This fully bypasses webpack/RSC ever parsing Ably's source, and was confirmed working: `npm run build` succeeded cleanly.
- **Acknowledged regressions, documented rather than hidden:** (1) presence/disconnect detection is now a best-effort `navigator.sendBeacon` fired on `pagehide` (a `"disconnect"` action, `markDisconnected`), not a guaranteed server-side `onClose` the way a Durable Object's WebSocket gave for free — matches the *original*, pre-PartyKit Supabase-era design's own heuristic, so this is a return to a previously-proven pattern, not a novel weakness; (2) idle-room cleanup is back to an hourly Vercel Cron (`GET /api/cron/cleanup`, re-added `vercel.json`) rather than a Durable Object's per-room `onAlarm`, since Ably has no per-channel timer primitive; (3) the in-memory rate limiter (`lib/multiplayer/rate-limit.ts`, unchanged code, reused as-is) is now scoped per-Vercel-serverless-function-instance rather than per-room the way a long-lived Durable Object scoped it — a real weakening, flagged explicitly in `SECURITY.md` as a recommended future fix (Neon- or Redis-backed counters) rather than glossed over.

# DATABASE.md

## Neon + Drizzle — the only database

- **Provider:** Neon (serverless Postgres), accessed via `@neondatabase/serverless`'s HTTP driver, wrapped by Drizzle ORM (`drizzle-orm/neon-http`) — HTTP-based, not raw-TCP, so no connection-pooling setup is needed from a stateless Next.js API route.
- **Schema file:** `src/lib/db/schema.ts` — **9 tables**: `profiles`, `matches`, `match_players`, `achievements`, `profile_achievements`, `recent_players`, `leaderboard_entries`, `public_room_listings`, `live_rooms`. Most of these hold durable, cross-match aggregates; `live_rooms` is the exception — see its own entry below for why it exists at all.
- **Migration files:** `drizzle/*.sql`, generated by `npm run db:generate`. **Never applied to a live database yet** — no `DATABASE_URL` has been supplied. Apply with `npm run db:migrate` once a real Neon connection string is in `.env.local`.
- **Client:** `src/lib/db/client.ts` — `getDb()`, a lazily-cached Drizzle instance. `server-only`. No admin-vs-scoped-client split — there's no RLS to scope a lesser-privileged client against, so every caller gets full access and is individually responsible for its own authorization (see `SECURITY.md`).
- **Env var:** `DATABASE_URL` (see `src/lib/db/env.ts`, `.env.example`). Not yet supplied — the whole stack is unverified against a live database.
- **Seed:** `src/lib/db/seed.ts`, run via `npm run db:seed` — populates the 5-row achievement catalog, upsert-safe (`onConflictDoNothing()`).

## Writers and readers

- **Writers:** `src/app/api/rooms/[code]/action/route.ts` (writes `live_rooms` on every accepted action; calls `finalize-match.ts` on match end, which writes `matches`/`match_players`/`profiles`/`leaderboard_entries`, then best-effort `recent_players` + achievements via `achievements.ts`; calls `public-rooms.ts`'s `syncPublicListing` to keep `public_room_listings` in sync), `src/app/api/cron/cleanup/route.ts` (deletes idle `live_rooms` rows + their listings), `src/app/api/profile/route.ts` (`PATCH` — updates a caller's own `displayName`/`avatarColor`), and `src/lib/identity/get-current-actor.ts` (provisions/claims `profiles` rows).
- **Readers:** `src/app/api/rooms/[code]/route.ts` (the initial-state fetch every client makes on mount, reads `live_rooms`), `src/app/profile/page.tsx` and `src/app/leaderboard/page.tsx` (both Server Components, both filtered to `getCurrentActor().profileId` where relevant — no RLS to lean on, so every query is explicit), `GET /api/public-rooms` (unauthenticated, reads `public_room_listings` only).

## Tables

### `profiles`

One row per player — guest or real account, decoupled from any auth provider.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `defaultRandom()`, no FK to any auth table |
| `clerk_user_id` | `text`, nullable, unique | set once a guest links a real account, or immediately for a fresh Clerk sign-up |
| `guest_cookie_id` | `text`, nullable, unique | set from day one for every guest (`guest_id` cookie value) |
| `display_name` | `text` | |
| `avatar_color` | `text` | default `'violet'` |
| `is_guest` | `boolean` | default `true` |
| `total_wins` | `integer` | default 0 |
| `games_played` | `integer` | default 0 |
| `favorite_game_id` | `text`, nullable | |
| `created_at`, `updated_at` | `timestamptz` | |

A profile can have `clerkUserId`, `guestCookieId`, both, or — very briefly, mid-provisioning — neither. Provisioning/claiming logic lives entirely in `src/lib/identity/get-current-actor.ts`, not a database trigger (no `security definer` functions exist under this schema at all).

### `matches`

Written once, when a match finishes (by `finalize-match.ts`, called from the room action route) — not a live/updated-during-play row.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `room_code` | `text`, nullable | informational only, no FK — there's no `rooms` table |
| `game_id` | `text` | not FK-constrained |
| `status` | `text` | check: `completed` \| `abandoned` |
| `seed` | `text` | the deterministic-RNG seed for this match |
| `modifiers` | `jsonb` | default `{}` |
| `winner_player_id` | `uuid`, nullable | `references profiles(id)` |
| `is_draw` | `boolean` | |
| `started_at`, `ended_at`, `created_at` | `timestamptz` | |

- **Index:** `status`.

### `match_players`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `match_id` | `uuid` | `references matches(id) on delete cascade` |
| `profile_id` | `uuid` | `references profiles(id) on delete cascade` |
| `seat` | `smallint` | |
| `result` | `text`, nullable | check: `win` \| `loss` \| `draw` \| `abandoned` |
| `score` | `integer` | default 0, set at finalization via `extract-score.ts` |

- **Constraints:** `unique(match_id, profile_id)`, `unique(match_id, seat)`.
- **Indexes:** `match_id`, `profile_id`.
- Populated from the match's `participants` snapshot (`StoredMatch.participants` in `room-state.ts`), captured at match start — **not** the live room roster, since `leaveRoom()` removes a departed player from the roster entirely, and their match result must still be recorded.

### `achievements`

Static catalog. `id` (`text` PK), `name`, `description`, `icon` (default `'trophy'`). Seeded rows (`src/lib/db/seed.ts`): `first-win`, `three-peat`, `all-rounder`, `word-wizard`, `perfect-game`.

### `profile_achievements`

Join table, `primary key (profile_id, achievement_id)`, `earned_at`. Only ever written by `src/lib/realtime/achievements.ts` after a match finalization.

### `recent_players`

`primary key (profile_id, opponent_id)`, `check (profile_id <> opponent_id)`, `times_played`, `last_played_at`.

### `leaderboard_entries`

`primary key (profile_id, game_id)`, `wins`/`losses`/`draws`/`games_played`, plus a **generated column** `win_rate` (`wins / games_played`, rounded to 4 decimal places, `0` if `games_played = 0`) computed by Postgres itself — portable as-is from the original schema this project started with, since Neon is plain Postgres. **Deserializes as a string, not a number**, via the neon-http driver — `/leaderboard`'s display code wraps it in `Number()` before doing display math (see `DECISIONS.md` D-016).

### `public_room_listings`

A **discovery index, not a source of truth** — `live_rooms` (below) remains the only authoritative owner of real room state. A row exists if and only if a room is currently public **and** still in its lobby (not yet started); the action route upserts or deletes it on every accepted action via `syncPublicListing()` (`src/lib/realtime/public-rooms.ts`); the cron cleanup route's idle-room sweep also removes it.

| Column | Type | Notes |
|---|---|---|
| `code` | `text` PK | |
| `selected_game_id` | `text`, nullable | |
| `player_count` | `integer` | default 0 |
| `max_players` | `smallint` | default 4 |
| `updated_at` | `timestamptz` | |

If this table and `live_rooms` ever disagree, `live_rooms` is right — treat a stale/missing listing row as a UX gap, not a correctness bug, since nothing authorization-sensitive depends on it.

### `live_rooms`

**The live room roster and in-progress match state — added specifically because Ably (the realtime transport) has no compute or storage of its own**, unlike the Cloudflare Durable Object this schema briefly didn't need to accommodate (see `DECISIONS.md` D-018). One JSONB row per active room, holding exactly the `StoredRoomState` shape `src/lib/realtime/room-state.ts` already operates on — not a normalized `rooms`/`room_players` split (that design was deliberately collapsed once already, per D-012, and there was no reason to re-introduce it here). A row is created on a room's first "join" action and deleted once the room closes or goes idle (`GET /api/cron/cleanup`, 4-hour threshold).

| Column | Type | Notes |
|---|---|---|
| `code` | `text` PK | the room code |
| `state` | `jsonb` | the full `StoredRoomState` blob |
| `updated_at` | `timestamptz` | bumped on every write; the cron sweep's idle-cutoff comparison |

**This table is not meant to accumulate history** — unlike `matches`/`match_players`, a row here reflects only the room's *current* state, overwritten wholesale on every action, and is deleted entirely once the room is done. If you need "what happened in this match," that's `matches`/`match_players`, written once at the end — not this table.

`LIVE_ROOMS` has no foreign-key relationships to the other tables — its `state` blob references `profiles.id` values internally (as plain UUID strings inside the JSON), but nothing at the schema level enforces that, since the whole point of this table is to hold ephemeral state that's discarded before it would ever need to be queried relationally.

## Storage buckets

None. No file storage of any kind is used anywhere in this app — avatars are just a named color, not an uploaded image.

## Sensitive data

- No PII beyond whatever email/OAuth identity a player links via Clerk's own sign-up flow — Clerk stores that itself; it is never duplicated into `profiles`.
- No payment data, no addresses, no phone numbers.
- `profiles` has no read restriction at the database layer — any server-side caller can read any row. This is a deliberate design choice (needed for leaderboards, opponent nicknames, etc., and there's no RLS to enforce a boundary even if one were wanted) but means `display_name`/`avatar_color`/win stats have no real privacy boundary between any two users. Flagged in `SECURITY.md`, not a bug.

## Known risks

1. `matches.game_id`, `match_players.result`, and similar `text` columns are constrained by a `check` constraint where one exists, but nothing DB-level validates `game_id` against the actual `GameId` union — that's enforced entirely in application code (`games/core/registry.ts`, Zod schemas). A malformed value could theoretically be inserted directly if application code had a bug — there's no RLS to catch it, since this schema has none by design.
2. No migration has ever actually been run against a real Postgres instance — everything above is a static reading of `schema.ts`, not an observed live schema.
